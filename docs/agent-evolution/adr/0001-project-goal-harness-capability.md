# ADR-0001：项目首要目标为 Agent Harness 工程能力建设

- 状态：Accepted
- 日期：2026-10-15
- 决策者：项目所有者
- 关联：[`data-agent-evolution-rfc.md`](../data-agent-evolution-rfc.md)、[`evaluation-plan.md`](../evaluation-plan.md)、[`open-issues.md`](../open-issues.md)
- 取代：无
- 影响：本 ADR 为后续全部 ADR 的前置约束

---

## 1. 背景与问题陈述

Data Agent 已具备文件与 PostgreSQL 分析、只读 SQL 防护、工具循环、报告、对话压缩、长期 Memory、运行追踪、评测与 MCP 接入能力。下一阶段的投入方向需要决策。

现有 RFC 的「目标与非目标」（§3）是按**产品质量**框架撰写的：目标表述为"意图识别稳定可解释""Memory 只注入相关内容""结论可追踪到证据"。这些都是合理的产品目标，但它没有回答一个更上层的问题：**这个项目存在的首要目的是什么。**

该缺失已经产生实际代价。近期的方案讨论在以下方向间反复摆动：

1. 垂直深耕数据分析能力
2. 向通用 Agent Harness 演进
3. 采用现成 Agent 框架并适配
4. 引入语义层（semantic layer / metric layer）解决业务口径问题

每一次摆动都是合理的——在**产品质量**这个隐含目标下，它们各自都是正确结论。特别是方向 4：语义层确实是业界对业务口径问题的标准解法（dbt MetricFlow、Cube、LookML、Snowflake Cortex Analyst 等均采用），它能让 `semantics_wrong` 类错误在结构上不可能发生。

**但语义层是数据治理能力，不是 Agent 工程能力。** 沿该方向深入，获得的是智能问数与 text-to-SQL 领域专长；而项目所有者期望获得的是 Agent Harness 工程能力：工作流编排、Memory 治理、工具调用治理、安全校验、Hooks 机制。

目标不写下来，每次讨论都会被产品逻辑重新拉回领域深耕方向。本 ADR 的作用是锚定目标，终止这种摆动。

---

## 2. 决策

**本项目的首要目标是 Agent Harness 工程能力建设。Data Agent 是载体，不是目的。**

据此确立三条约束：

| 编号 | 约束 |
| --- | --- |
| C-1 | 领域（数据分析）能力的投入以**"不成为瓶颈"为上限**，不以"达到领域最优"为目标 |
| C-2 | 架构选择优先考虑**能力建设价值**，而非实施成本最小化 |
| C-3 | 评测体系的作用从"证明产品质量"转为**"验证 Harness 改动安全"** |

---

## 3. 推论

### 3.1 C-1 的具体含义

领域侧只做"摘除瓶颈"级别的修复，完成即停止：

| 项目 | 处理 | 理由 |
| --- | --- | --- |
| A-01 PostgreSQL 列级 schema 缺失 | **修复** | 模型须猜列名，是当前最大的单点准确率拖累；约一小时改动 |
| A-02 方言解析不一致 | **修复** | 本质是工具契约问题，不是数据治理问题 |
| 语义层 / metric layer | **不做** | 见 §4 |
| text-to-SQL 技法（候选生成重排、self-consistency、schema linking 专用模型） | **不做** | 领域专长，非 Agent 工程 |

### 3.2 C-2 的具体含义

**Harness 治理层自行实现，传输层使用现成 SDK。**

| 层 | 处理 | 理由 |
| --- | --- | --- |
| Tool Registry、Hooks、Policy 引擎、预算控制、Context 治理 | **自行实现** | 这些即学习内容本身，外包等于不学 |
| Provider 适配、流式、底层重试 | **用 SDK** | 已在用 `openai` SDK，无学习价值 |

注意该结论与"采用 Pydantic AI 承载核心循环"的早期倾向不同。早期倾向的前提是**节省重复劳动**；在 C-2 下该前提不再成立。本条不排除后续为单一子问题引入框架（例如为审批流与长运行恢复评估 LangGraph 的 `interrupt` 与 checkpointer），但须单独立 ADR 论证。

### 3.3 C-3 的具体含义

评测（`evals/`、`EvalSuite`/`EvalCase`/`EvalRun`）**重新归类为 Agent 基础设施，而非数据资产**。

它是验证任何 Harness 改动（Tool Registry 重构、Hooks 引入、Context 预算调整、框架替换）是否造成回归的唯一手段。因此评测闭环**保留并继续投入**，这是 C-1 的唯一例外。

## 4. 明确非目标

以下内容在本 ADR 有效期内为**明确非目标**，不得在未取代本 ADR 的前提下重新纳入范围：

1. **语义层 / metric layer**（指标定义建模、measure/dimension 编译器、治理查询路径）
2. **text-to-SQL SOTA 追赶**（对标 Spider 2.0 / BIRD 排行榜）
3. **智能问数产品化**（面向业务用户的问数产品形态打磨）
4. **数据治理能力建设**（数据血缘、数据质量体系、指标管理平台）
5. 多 Agent 团队与自治 Agent（沿用 RFC §3.2 既有判断）
6. 业务数据库写入能力（沿用 RFC §3.2 既有判断）

记录此节的目的是防止范围回爬。这些方向本身并无问题，其中若干（尤其第 1 项）在产品目标下是正确选择——它们只是与本项目目标不符。

---

## 5. 备选方案与否决理由

| 方案 | 内容 | 否决理由 |
| --- | --- | --- |
| A. 垂直深耕数据分析 | 投入语义层、text-to-SQL 技法、数据画像深化 | 获得的是数据治理与领域专长，与目标不符 |
| B. 整体迁移到现成框架 | 采用 Pydantic AI / LangGraph 承载全部编排 | 治理层被框架吸收，恰好跳过学习内容；见 §3.2 |
| C. 另起通用 Harness 项目 | 抛弃 Data Agent，从零写框架 | 丢弃已有的真实约束（多租户、凭据、只读强制、真实工具），退化为玩具；真实约束正是学习价值所在 |
| D. **本方案** | Data Agent 作载体，领域投入设上限，治理层自建 | 保留真实约束，投入指向目标能力 |

方案 C 的否决理由值得强调：**这个载体最有价值的部分恰是它的真实性。** SQL 是高风险、结构化、可静态校验的工具调用；多租户隔离、凭据加密、最小权限、只读强制是真实的安全约束。绝大多数从零搭建的 Agent 框架练手项目没有这一层，因而学不到工具调用治理与安全校验。

---

## 6. 载体适配性评估

本载体对目标能力的覆盖**并不均匀**，需如实记录：

| 目标能力 | 适配度 | 说明 |
| --- | --- | --- |
| 工具调用治理 | 高 | SQL 是高风险、结构化、可静态校验的工具调用，比一般 API 调用丰富 |
| 安全校验 | 高 | 只读强制、多租户隔离、最小权限角色、凭据加密均为真实约束 |
| Memory 治理 | 中高 | 业务口径与用户偏好是具备生命周期与冲突的真实长期 Memory |
| Hooks | 中（载体无关） | 任何载体均可承载，本项目无特殊优势亦无劣势 |
| **工作流编排** | **低** | 见下 |

### 6.1 工作流编排的载体缺陷

**数据问答在本质上不需要工作流。** 典型路径为 inspect → query → answer，RFC §8.1 自身即规定"简单请求不生成计划"。编排能力需要长时程、分支、并行、失败恢复、审批门等特征，问答场景基本不具备。

项目内具备真实工作流形态的三处场景，应作为编排能力的练习载体：

| 场景 | 工作流特征 | 现有基础 |
| --- | --- | --- |
| Eval 批量运行 | 150 用例 × 3 次重复 = 450 次 run；并发控制、部分失败、断点续跑、进度上报、成本预算、超时 | `EvalRun` 模型已存在 |
| 定时与周期报告 | 多步（查询→图表→叙述→投递）、失败重试、发送前人工审批 | `Report`/`ReportVersion` 已存在 |
| Subagent 扇出聚合 | 跨多连接并行分析后聚合 | `AgentRun.parent_run_id` 字段已建但未使用 |

### 6.2 第二工具域作为检验手段

仅服务于 13 个 SQL 类工具的 Harness，其抽象会被 SQL 隐性塑形而难以自察。

因此确立一项检验手段：**引入一个与数据分析无关的工具域**（文件系统操作、web fetch、代码执行或外部 API），用以暴露 Tool Registry、权限模型与 Context 预算中的漏抽象。

这是判断产出"是 Harness 还是 Data Agent"的最低成本检验。

## 7. 后果

### 7.1 正面

- 投入方向与目标能力对齐，不再因隐含产品逻辑反复摆动。
- 保留真实约束（多租户、凭据、只读强制），学习内容具备生产相关性。
- 领域投入设上限后，Harness 层获得明确的时间与注意力预算。
- 决策依据公开：后续 ADR 可直接引用 C-1 / C-2 / C-3 判断取舍。

### 7.2 负面

- **产品竞争力不再是优化目标。** 本项目不会成为优秀的智能问数产品，这是本决策的自觉代价。
- 领域质量停留在"不成为瓶颈"水平，`semantics_wrong` 类错误将长期存在。
- 自建治理层的实现质量短期内低于成熟框架。
- 工作流编排能力受载体限制，须依赖 §6.1 的三处场景，覆盖不如专门项目。

### 7.3 对现有文档的影响

| 文档 | 影响 |
| --- | --- |
| RFC §3「目标与非目标」 | 该节为产品框架表述，现受本 ADR 约束；冲突时以本 ADR 为准 |
| RFC §11.1 规划的 ADR 列表 | 原列表以 `0001-use-single-orchestrator` 起编；本 ADR 占用 0001，原列表顺延至 0002 起 |
| `open-issues.md` ISSUE-001 / ISSUE-002 | 两者修复路径均指向语义层与口径声明能力，依 §4 降级为 Deferred；**条目保留不删除**，记录判断过程 |
| `evaluation-plan.md` §9 | 评测定位依 C-3 变更；现有可重复性契约（数据哈希、锁文件、三次运行、stable pass）全部保留并继续适用 |

## 8. 风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| 领域反馈信号不足，Harness 改动无法验证是否造成回归 | 保留 Eval 闭环作为 Agent 基础设施（C-3 例外条款）；每项 Harness 改动须有前后对照 |
| 自建治理层质量不及框架，产出不可用 | 接受质量差距为学习成本；仅在传输层使用 SDK；关键子问题可单独立 ADR 引入框架 |
| 范围回爬至语义层 | §4 显式记录非目标；范围变更须以新 ADR 取代本 ADR，不得在实现 PR 中隐式引入 |
| 领域质量过低导致载体失真，无法暴露真实治理问题 | A-01 / A-02 修复为前置条件；"不成为瓶颈"由 Eval 失败分类的分布判定，而非主观判断 |
| 过度泛化：为通用性牺牲可用性 | §6.2 的第二工具域是检验手段，不是产品需求；泛化程度以"能暴露漏抽象"为上限 |

---

## 9. 复核条件

出现以下任一情形时应复核本 ADR，必要时以新 ADR 取代：

1. 项目目标变更为产品化或对外交付。
2. Harness 层核心能力（Tool Registry、Hooks、Policy、预算、Context 治理）已建成并经第二工具域检验通过——此时继续投入的边际价值下降，可重新评估领域方向。
3. Eval 失败分类显示领域质量已严重失真，`A-01`/`A-02` 修复后仍无法暴露治理层问题。
4. 发现本载体对目标能力的覆盖缺口大于 §6 的评估（尤其工作流编排）。
